# End-to-end tests (`e2e/`)

Detail behind the testing rules in `CLAUDE.md`. Read this before adding or changing a Playwright spec.

- Every change that affects behavior updates or adds the matching Playwright test in `e2e/` in the same commit. Run `cd e2e && npx playwright test` before pushing (`BASE_URL=http://localhost:8124` for a local server: `node e2e/local-server.mjs 8124` serves this checkout at `/vedic-math/` and proxies the rest of the site from https://sbmadhav.com). A targeted run (`--project=chromium tests/<spec>.spec.ts`, or `-g "<test name>"`) is the normal loop; the full three-project suite is for the final check before a push.
- The suite targets the LIVE https://sbmadhav.com/vedic-math/ by default (projects chromium, webkit, mobile). First run: `cd e2e && npm ci && npx playwright install chromium webkit`.
- Never write to production Firestore from a test. `e2e/tests/fixtures.ts` replaces the Firebase SDK with a fake that records attempted writes (`cloudLog(page)`), and aborts and fails the test on any write-shaped request to `firestore.googleapis.com`. Only `leaderboard.live.spec.ts` loads the real SDK (reads only, no sign-in and no Auth SDK, chromium, no retries). Never submit an Arena or game score against the live backend.
- The service worker is blocked (`serviceWorkers: 'block'` in `e2e/playwright.config.ts`) everywhere except `e2e/tests/offline.spec.ts`. Two reasons: Playwright WebKit does not route requests from a worker-controlled page, so the fake SDK and the local GoatCounter answer are bypassed there (real anonymous sign-ins, counted visits); and a worker installing in every fresh test context roughly doubles the requests and gets the IP rate limited by GitHub Pages (HTTP 429, every test then times out). Keep offline specs off WebKit and keep their tripwire for live Google backends.
- Analytics never counts a test run: `fixtures.ts` answers GoatCounter locally, and specs that check events replace `/assets/analytics.js` with a stub that records `window.siteTrack` calls.
- Known axe violations go in `KNOWN` in `e2e/tests/a11y.spec.ts` (each becomes a `test.fixme` with a note); remove the entry when fixed.
- `e2e/tests/cov/` holds one spec per live OpenSpec scenario, named `<spec>-<n>.spec.ts`, with a comment naming the requirement and scenario. In CI they run on chromium only, and the run after a push leaves them out (`E2E_SKIP_COV=1`), so the live run stays under GitHub Pages' rate limit and the job timeout. Locally every project runs them. Archiving an OpenSpec change adds the coverage specs for the scenarios it makes live.
- The live pages carry a Content-Security-Policy without `'unsafe-eval'`: never build a function from a string inside `page.evaluate` (`new Function`, `eval`); pass a named option and keep the code in the page function.
- `.github/workflows/e2e.yml` runs the suite daily (06:23 UTC), on demand (optional `base_url`) and on pushes to `main` (after waiting for the Pages deploy). The daily and manual runs also check every Watch shelf video on YouTube (`tests/videos.live.spec.ts`, tagged `@live-videos`).
- Fake browser APIs (speech, camera) are installed with `page.addInitScript` before `open()`; the verses specs are the pattern for a fake `speechSynthesis`.
- Under a faked clock, end a timed round with `page.clock.fastForward(61_000)`: the round's next animation frame reads the time and ends it. `runFor` fires every timer on the way, about 3,800 animation frames for a 60 second round, which on a busy machine took about 30 s of real time per round and ran tests past their budget. Keep `runFor` for timers that must each fire (a countdown, the weekly Sparks post's wait). Install a clock a little before the time you pause at: an installed clock runs, so `pauseAt` the install time is already in the past.
- A fake device must behave like the real one in the way the app relies on: the fake camera is already sending frames when `getUserMedia` resolves (a canvas stream handed over before its first frame was now and then never loaded by Linux WebKit), and a test that is not about idle scheduling can make `requestIdleCallback` answer at once (a busy browser gives idle callbacks only at their timeout).
